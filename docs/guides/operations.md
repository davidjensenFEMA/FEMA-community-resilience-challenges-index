## Database backups

### Creating a backup

```bash
# Timestamped backup (default)
./scripts/database_backup.sh

# Backup with custom name (gets timestamp suffix anyway)
./scripts/database_backup.sh pre_2024_rerun
```

Backups land in `<repo>/backups/` (project root level, **not** `data/backups/`). Format: `cria_backup_YYYYMMDD_HHMMSS.sql.gz`.

The script:
- Verifies the `cria_postgres` Docker container is running
- Reports per-table row counts before backup
- Pipes `pg_dump` through `gzip`
- Warns if you have >30 backups (suggests a `find ... -mtime +30 -delete` cleanup)

**When to back up**:
- Before any pipeline rerun that uses the database (so a calibration regression can be reverted)
- Before migrations (`alembic upgrade head`)
- Before bulk DELETEs or schema changes
- On a periodic schedule for production data

### Restoring a backup

```bash
./scripts/database_restore.sh backups/cria_backup_20260415_103000.sql.gz
```

The script will:
1. Verify the container is running
2. Show current database statistics
3. **Prompt for `yes/no` confirmation** before destroying data
4. `TRUNCATE` all CRCI tables (`aggregate_indicators, indicators, source_data, geographies, data_years, reference_indicators` with `CASCADE`)
5. Decompress (if `.gz`) and pipe into `psql`
6. Report restored row counts

**Pre-restore checklist**:
- The target database must already have the schema (`alembic upgrade head` first if it doesn't)
- The `TRUNCATE` will fail if any of the 6 tables don't exist
- Restoring into a production database — back up the current state first (`./scripts/database_backup.sh pre_restore`)

### Restoring to a different database name

The script hard-codes `DB_NAME=cria_db`. To restore into a differently-named target:
1. Edit the `DB_NAME` variable in `scripts/database_restore.sh`
2. Or restore manually:

```bash
gunzip -c backups/cria_backup_20260415_103000.sql.gz | \
  docker exec -i cria_postgres psql -U cria_user -d <target_db>
```

### Backup retention

There's no automated rotation. The script warns at 30+ backups; the suggested cleanup is:

```bash
find backups/ -name 'cria_backup_*.sql.gz' -mtime +30 -delete
```

Wire this into a cron job for production. There's no built-in scheduler.

## Database migrations (Alembic)

CRCI uses Alembic for schema versioning. Migration scripts live in `alembic/versions/`.

### Apply pending migrations

```bash
poetry run alembic upgrade head
```

Run this:
- After cloning a fresh repo with PostgreSQL
- After pulling in changes that touched `src/db/models.py`
- Before restoring a backup if the schema doesn't exist

### Inspect migration state

```bash
poetry run alembic current        # Current revision in the database
poetry run alembic history --verbose  # Full history
poetry run alembic heads          # Latest revision(s) — should be one
```

### Create a new migration

After modifying `src/db/models.py`:

```bash
poetry run alembic revision --autogenerate -m "Add new column to source_data"
```

This generates a script in `alembic/versions/`. **Always review autogenerated migrations** before applying:
- Autogenerate misses some changes (server defaults, named constraints, type changes)
- For SQLite compatibility, you may need to set `render_as_batch=True` in the migration
- Inspect both `upgrade()` and `downgrade()` paths

Then apply:

```bash
poetry run alembic upgrade head
```

### Downgrade

```bash
poetry run alembic downgrade -1     # Back one step
poetry run alembic downgrade <rev>  # To a specific revision
poetry run alembic downgrade base   # To empty
```

Make sure to back up first.

### SQLite vs PostgreSQL gotcha

SQLite does not support all `ALTER TABLE` operations (notably column rename and column drop without recreation). For migrations that need to be portable to both:

```python
def upgrade():
    with op.batch_alter_table("source_data") as batch_op:
        batch_op.alter_column("old_name", new_column_name="new_name")
```

The `batch_alter_table` context manager handles the create-temp-and-copy dance for SQLite.

## Multi-year persistence and querying

PostgreSQL supports multiple years of data side-by-side. Each row in `source_data`, `indicators`, and `aggregate_indicators` has a `year` column.

### Query examples

Year-over-year change in CRCI for a single county:

```sql
SELECT
    year,
    cri,
    cria_p
FROM aggregate_indicators
WHERE geo_id = '0500000US01001'
ORDER BY year;
```

Counties whose `cri` changed by > 0.5 between 2022 and 2024:

```sql
SELECT
    a2024.geo_id,
    a2024.cri AS cri_2024,
    a2022.cri AS cri_2022,
    a2024.cri - a2022.cri AS delta
FROM aggregate_indicators a2024
JOIN aggregate_indicators a2022
  ON a2024.geo_id = a2022.geo_id
 AND a2024.year = 2024
 AND a2022.year = 2022
WHERE ABS(a2024.cri - a2022.cri) > 0.5
ORDER BY ABS(a2024.cri - a2022.cri) DESC;
```

**Important caveat**: CRCI z-scores are recomputed each year. A change in `cri` between 2022 and 2024 reflects both the focal county's movement *and* the rest of the population's movement. See [methodology.md "Cross-year comparability"](methodology.md#cross-year-comparability).

### Dropping a single year

To remove a year's data without affecting other years:

```sql
BEGIN;
DELETE FROM aggregate_indicators WHERE year = 2024;
DELETE FROM indicators WHERE year = 2024;
DELETE FROM source_data WHERE year = 2024;
COMMIT;
```

(Always run inside a transaction in case of typos.)

After dropping a year, re-running the pipeline for that year will work without `--no-db`.

## Observability for long-running pipelines

The tract pipeline runs ~2 hours. Observability options:

### Stdout/log location

By default, `scripts/run_full_pipeline.py` logs to stdout via `src/utils/logger.py`. There's no built-in log file; redirect manually:

```bash
poetry run python scripts/run_full_pipeline.py \
  --geography tract --year 2024 --export-excel --timeout 240 \
  2>&1 | tee logs/tract_2024.log
```

### Key log lines to watch for

| Log message | Meaning |
|-------------|---------|
| `--- Step 1: Pulling Source Data ---` | Pulling from APIs (slow for tract: ~30 min) |
| `Pulling data for state XX/52` | Per-state tract iteration (52 calls) |
| `Saving source data to database...` | The slowest phase for tract (~63 min for 88K rows) |
| `--- Step 2: Calculating Indicators ---` | Fast (<5 min) |
| `--- Step 3: Creating Aggregate Scores ---` | Includes binning; ~10–20 min for tract |
| `Pipeline timeout set to N minutes` | Confirm your `--timeout` was applied |

### Estimating progress

There's no progress bar. Rough thumbnail for tract 2024:

| Phase | Wall time |
|-------|-----------|
| API pulls (52 states) | ~30 min |
| DB save (source_data) | ~63 min |
| Indicators calc | ~3 min |
| Aggregator (z-scores, binning) | ~15 min |
| Excel export | ~5 min |
| **Total** | **~2 hours** |

Use these as benchmarks. If you're 30 minutes in and still seeing `Pulling data for state 03/52`, something is throttling you.

### What if SIGALRM fires?

The timeout (default 60 min, recommended 240 min for tract) is a hard kill via `SIGALRM`. After it fires:

1. The pipeline exits non-zero.
2. **Partial state may be in the database** — source_data rows for partially-pulled states are committed; indicators/aggregates are not.
3. Re-running with `--skip-pull` will reuse what's there *if* the DataPuller cache logic detects existing rows; otherwise re-running without `--no-db` will trip `UniqueViolation` on the partial source_data.
4. Cleanest recovery: delete the partial year (`DELETE FROM source_data WHERE year = 2024`), bump `--timeout`, re-run.

## Re-pulling source data when an upstream API revises figures

The pipeline does not auto-detect when the Census, CBP, EAVS, ARDA, or POP source data has been revised. To force a fresh pull and overwrite:

```bash
# Step 1: Drop the existing source data for the year
psql -U cria_user -d cria_db -c "
  BEGIN;
  DELETE FROM source_data WHERE year = 2024;
  DELETE FROM indicators WHERE year = 2024;
  DELETE FROM aggregate_indicators WHERE year = 2024;
  COMMIT;
"

# Step 2: Re-run the pipeline (will pull fresh data and re-write)
poetry run python scripts/run_full_pipeline.py \
  --geography county --year 2024 --export-excel
```

There's no `--force-repull` CLI flag. If you do this often, propose one.

## API rate limits

| API | Rate limit | What happens at limit |
|-----|------------|----------------------|
| Census ACS | 500 calls/day per key (unauthenticated: lower) | HTTP 429, no automatic retry |
| Census CBP | Same as ACS | Same |
| EAVS | None (file download) | — |
| ARDA | None (local file) | — |
| POP | None (file download) | — |

The county pipeline uses ~10–20 Census calls; tract uses ~52 per indicator group (per-state iteration). A single tract pipeline run will not exhaust the daily quota.

If you hit a 429:
1. Wait — the limit resets at midnight UTC.
2. Check your `CENSUS_API_KEY` is set (unauthenticated requests have a much lower limit).
3. There is **no automatic retry** in `src/api/base_client.py`; you must re-run the pipeline.

## When to switch from SQLite to PostgreSQL

SQLite is fine for:
- Development
- State and tribal pipelines (small data)
- One-off county runs you're going to throw away
- Solo work — no concurrent writers

Switch to PostgreSQL when any of:
- **Cross-year queries** are needed (the `year` column join patterns above)
- **>1 concurrent writer** (SQLite serializes; will block)
- **Durability across `rm cria.db`** is needed (production)
- **Tract scale** — 88K rows × source columns can OOM SQLite or run very slowly
- **Backup/restore lifecycle** is needed (the scripts only support PostgreSQL)
- Multiple developers sharing a database

## Performance targets

| Operation | Target | Notes |
|-----------|--------|-------|
| State pipeline | < 5 min | If slower, check Census API latency |
| County pipeline | < 15 min | DB save phase dominates |
| Tract pipeline | < 2.5 hours | DB save (~63 min) + per-state iteration (~30 min) |
| Tribal pipeline | < 5 min | Smallest dataset |
| `bulk_create()` for 88K rows | < 5 sec | If slower, you're using ORM `add_all()` instead |
| Coverage report | < 30 sec | `pytest --cov=src` |

## Disk space

| Geography | Excel output size | DB row footprint |
|-----------|-------------------|------------------|
| State | < 1 MB | ~1 MB |
| County | ~50 MB across 3 workbooks | ~100 MB |
| Tract | ~500 MB across 3 workbooks | ~5 GB |
| Tribal | ~5 MB | ~30 MB |

Tract is the killer — make sure your `data/output/` and PostgreSQL data directory have at least 10 GB free.
